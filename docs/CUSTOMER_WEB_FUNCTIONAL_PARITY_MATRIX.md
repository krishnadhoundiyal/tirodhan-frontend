Mobile reference: `d0a9ab15a7436d2329b6af103775c72ff1bfc969`, tree verified against fetched origin/main. Backend inspected read-only: `b281e03a47d202fd8b5c3d895075aa358062c5fa`. Its test fails if the reference changes or a route has no recorded equivalent. CI watches Mobile paths and the Customer Web test cache includes those inputs. Refreshing the snapshot requires repeating this audit; the script does not establish parity by itself.

- **Implemented**: real browser UI, clients/state and local test coverage exist. All live CUSTOMER access additionally shares gate A below.
- **Implemented / same backend gate**: Mobile UI/client exists, but its backend capability is absent at the verified backend HEAD. Web equivalent and isolated fixtures are implemented; production rejects before HTTP.
- **Implemented / browser prerequisite**: business workflow is implemented with a browser port; real browser environment/provider approval is pending. This is not an omitted implementation or live acceptance claim.

Mobile runtime reads EXPO_PUBLIC_CUSTOMER_CAPABILITIES (default empty), requires its approved API environment, and separately isolates SCREEN_PREVIEW. Backend-available below means verified server code plus an implemented Mobile client; no deployed Mobile environment or live feature activation is inferred. Its current native checkout composition is null.

There are **no unmapped current Mobile screens or omitted customer business functions** in this audited baseline. Production release is not accepted: the approvals and live checks below remain necessary.

## Verified gates and remaining acceptance

**A — APIM browser authentication:** Issues [#13](https://github.com/krishnadhoundiyal/tirodhan-frontend/issues/13) and [#14](https://github.com/krishnadhoundiyal/tirodhan-frontend/issues/14) remain open (rechecked 25 October). No approved gateway/resources/origins/routes/cookies/CSRF. Concrete adapter remains uncomposed. Real cookie stripping/attributes, CORS/CSRF, separate Customer/Operations sessions, revocation, stalled multi-tab ordering and measured latency must be proven. All authenticated workflows are implemented and locally tested behind this gate.

**B — same absent Mobile backend capabilities:** profile, preferences, favourites, content, feedback, paymentMethods, notifications and native push-device registration have client/UI implementations but no matching server routes at the inspected HEAD. Do not turn on flags based on fixture tests. Current backend catalogue/quote/projection/hold/booking/history/finance/refund/cancellation-compensation are implemented and are not classified as missing.

**C — browser checkout:** approved nonproduction customer origin, Razorpay test merchant/public key provisioning, script/frame/connect CSP and real provider/backend webhook/reconciliation acceptance. Current Mobile main itself composes `nativeCheckout: null`; prior native-branch reports are not evidence of merged/runtime availability. Browser adapter/financial state machine are implemented. No real checkout/payment/refund occurred here; production keys are rejected by the test-only factory.

**D — maps/geocoding:** browser geolocation/manual address/keyboard pin work without a third-party provider. Interactive tiles and geocoding require approved HTTPS provider URLs, privacy review and attribution. These are deployment inputs, not hardcoded guesses. Same Mobile native geocoder behavior is implemented using a browser provider port and concrete configurable Nominatim-compatible adapter.

**E — Web Push:** browser subscription endpoint/payload/auth/revocation, VAPID and environment/service-worker approval. Native push token endpoint is not a browser contract. Full permission/subscription/revocation/signal/history behavior is implemented/tested through a port; no backend URL invented. Real push delivery/device testing remains unproven.

Hosting/public origin/legal/support copy and real API deployment/idempotency retention/reconciliation are still release prerequisites. No merge/deploy/PR/provisioning or other app change is part of this correction. Local fixture evidence establishes parity implementation; it is not production activation or real-device/provider acceptance.
